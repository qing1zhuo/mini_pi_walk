# Mini Pi RL Baseline：接入自定义强化学习算法

本文针对 `Mini_Pi_RL_Baseline` 当前代码结构，说明怎样在保留原有 `pai_ppo` 任务的同时，添加自己的算法。文中的 `MyPPO` 是**接线示例**，不是一种新算法；真正的算法目标函数、更新规则和测试仍需按你的设计实现。

## 1. 先确定要改哪一层

训练链路是：

```text
humanoid/scripts/train.py
  -> humanoid/utils/task_registry.py
  -> humanoid/envs/pai/pai_env.py（PaiFreeEnv，Isaac Gym 环境）
  -> humanoid/algo/ppo/on_policy_runner.py（采样与训练调度）
  -> humanoid/algo/ppo/ppo.py（参数更新）
  -> humanoid/algo/ppo/actor_critic.py（策略与价值网络）
```

| 想做的事 | 建议改动 |
| --- | --- |
| 只调整学习率、网络宽度、PPO 超参数 | 在训练配置中修改；不必新增算法类 |
| 修改 PPO 损失、GAE 或优化步骤 | 新增 on-policy 算法类，尽量复用现有 Runner 与 RolloutStorage |
| 更换 Actor/Critic 网络 | 新增网络类，并让 Runner 能导入它 |
| 接入 SAC、TD3 等 off-policy 算法 | 新增 ReplayBuffer、算法类及 Runner；不能直接复用 PPO 的训练循环 |

环境接口见 `humanoid/algo/vec_env.py`：`step(actions)` 返回 `(obs, privileged_obs, rewards, dones, infos)`。当前 `PaiFreeEnv` 的 Actor 输入是 `15 × 47 = 705` 维历史观测，Critic 输入是 `3 × 73 = 219` 维特权观测，动作是 12 个关节控制量。环境配置在 `humanoid/envs/pai/pai_config.py`。

## 2. 最小接入：新增一个 on-policy 算法

如果算法仍使用固定长度的 rollout、GAE 和多轮 mini-batch 更新，可以沿用 `OnPolicyRunner`。建议给新算法独立的目录、任务名和实验目录，避免覆盖基线：

```text
Mini_Pi_RL_Baseline/
└── humanoid/
    ├── algo/
    │   └── my_ppo/
    │       ├── __init__.py
    │       └── my_ppo.py
    └── envs/
        ├── __init__.py
        └── pai/pai_config.py
```

### 第一步：写算法类

`humanoid/algo/my_ppo/my_ppo.py` 的最小骨架：

```python
from humanoid.algo.ppo.ppo import PPO


class MyPPO(PPO):
    def __init__(self, actor_critic, auxiliary_loss_coef=0.1, device="cpu", **kwargs):
        super().__init__(actor_critic=actor_critic, device=device, **kwargs)
        self.auxiliary_loss_coef = auxiliary_loss_coef

    def update(self):
        # 接线阶段先调用原 PPO 更新，验证任务注册、训练与保存链路。
        # 实现新算法时，用你的目标函数与更新步骤替换这里。
        return super().update()
```

`humanoid/algo/my_ppo/__init__.py`：

```python
from .my_ppo import MyPPO
```

复用 `OnPolicyRunner` 时，算法须兼容它调用的接口：

```text
init_storage(num_envs, num_steps, actor_obs_shape, critic_obs_shape, action_shape)
act(obs, critic_obs) -> actions
process_env_step(rewards, dones, infos)
compute_returns(last_critic_obs)
update() -> (mean_value_loss, mean_surrogate_loss)
```

Runner 还直接读取 `alg.actor_critic`、`alg.optimizer`、`alg.learning_rate`，用于推理、日志、保存和恢复。继承 `PPO` 可以先保留这些约定。实现自己的 `update()` 时，参考 `ppo.py` 中的 mini-batch 迭代、梯度更新和末尾的 `self.storage.clear()`；如果增加训练指标，现有 Runner 的双值解包和日志代码也要同步改。

### 第二步：让 Runner 找到新类

当前 `humanoid/algo/ppo/on_policy_runner.py` 用 `eval(self.cfg["algorithm_class_name"])` 创建算法。必须在**这个文件的模块作用域**导入新类：

```python
from humanoid.algo.my_ppo import MyPPO
```

只在 `humanoid/algo/__init__.py` 导出 `MyPPO`，但没有导入到 `on_policy_runner.py`，并不足以让这里的 `eval()` 找到它。长期维护时可把 `eval()` 改为显式注册表，例如 `{"PPO": PPO, "MyPPO": MyPPO}`。

### 第三步：添加独立训练配置

在 `humanoid/envs/pai/pai_config.py` 中，接在 `PaiCfgPPO` 后新增：

```python
class PaiCfgMyPPO(PaiCfgPPO):
    class algorithm(PaiCfgPPO.algorithm):
        auxiliary_loss_coef = 0.1

    class runner(PaiCfgPPO.runner):
        algorithm_class_name = "MyPPO"
        experiment_name = "Pai_my_ppo"
        run_name = "v1"
```

`class algorithm` 中的字段会作为关键字参数传给算法构造函数；新字段要由 `MyPPO.__init__()` 接收，继承的 PPO 字段由 `**kwargs` 继续传给父类。若要改网络宽度，可另加 `class policy(PaiCfgPPO.policy)` 覆盖 `actor_hidden_dims`、`critic_hidden_dims`；网络类本身不变时无须改 `policy_class_name`。

### 第四步：注册新任务

在 `humanoid/envs/__init__.py` 导入配置，并保留原来的 `pai_ppo` 注册：

```python
from .pai.pai_config import PaiCfg, PaiCfgPPO, PaiCfgMyPPO

task_registry.register("pai_ppo", PaiFreeEnv, PaiCfg(), PaiCfgPPO())
task_registry.register("pai_my_ppo", PaiFreeEnv, PaiCfg(), PaiCfgMyPPO())
```

这样两个任务共用同一个 Mini Pi 环境，但算法、超参数和日志目录分开。`TaskRegistry` 会根据 `runner_class_name` 创建 Runner；当前例子继承了 `OnPolicyRunner`，不需要额外修改 `task_registry.py`。

## 3. 编写真正的更新规则

接线跑通后，在 `MyPPO.update()` 中实现自己的训练目标。可从现有 `PPO.update()` 复制训练循环，再按算法需要更换：

1. 从 `self.storage.mini_batch_generator(...)` 取出观测、动作、旧策略概率、优势和 return。
2. 用当前 Actor/Critic 重新计算策略分布与价值。
3. 构造你的策略损失、价值损失和辅助损失。
4. 调用 `optimizer.zero_grad()`、`loss.backward()`、梯度裁剪和 `optimizer.step()`。
5. 汇总指标、执行 `self.storage.clear()`，并按 Runner 约定返回两个数值。

不要把示例中的 `super().update()` 当作新算法：它仍然执行原始 PPO。若你的方法改变了数据需求（例如额外的目标状态、潜变量或历史序列），还需同步扩展 `RolloutStorage.Transition`、`RolloutStorage` 和 `act()/process_env_step()` 保存的数据。若改变了网络输入输出，则还要检查 `PaiFreeEnv.compute_observations()` 与部署端的观测构造。

## 4. 训练、验证与导出

以下命令应在 `Mini_Pi_RL_Baseline` 目录、已安装 Isaac Gym 的 Linux 环境中运行。先做小规模冒烟测试：

```bash
WANDB_MODE=offline python humanoid/scripts/train.py \
  --task=pai_my_ppo --run_name=smoke \
  --num_envs=64 --max_iterations=2 --headless
```

检查是否创建 `logs/Pai_my_ppo/<时间>_smoke/`，是否有 `model_*.pt`，以及 loss 和奖励是否为有限值。训练器每轮采集 `num_envs × num_steps_per_env` 条 transition；默认每环境 24 步，64 环境即 1536 条。确认能正常保存、加载后，再增加环境数和训练轮次。

`humanoid/scripts/play.py` 会强制从 checkpoint 恢复，并调用 `runner.get_inference_policy()`；导出函数还直接取 `runner.alg.actor_critic.actor`。所以复用当前 Actor-Critic 的算法通常可沿用现有导出流程。若使用全新网络或分离的 Actor，必须相应调整 `play.py` 和 `humanoid/utils/helpers.py` 的导出逻辑。

**注意：**当前 `helpers.py` 的 ONNX 导出示例输入硬编码为 705 维，导出文件名为 `policy_onnx.onnx`；TorchScript 文件名为 `policy_torch.pt`。如果你改了观测维度，要同步修改导出输入及 `humanoid/scripts/sim2sim.py` 的观测拼接。`sim2sim.py` 还依赖 12 维动作顺序和 MuJoCo/URDF 的关节映射，不能只确认训练成功就认为策略可部署。

## 5. SAC、TD3 等 off-policy 算法

Off-policy 不适合只继承 `PPO.update()`。现有 Runner 的行为是“收集固定长度 rollout → 算 GAE → 多轮更新 → 清空存储”，而 SAC/TD3 通常需要持续保留 transition、随机回放、目标网络，以及不同的 Actor/Critic 更新频率。建议另建：

```text
humanoid/algo/sac/
├── replay_buffer.py
├── actor_critic.py
├── sac.py
└── off_policy_runner.py
```

新 Runner 需要满足 `TaskRegistry.make_alg_runner()` 的构造调用形式：

```python
runner = OffPolicyRunner(env, all_cfg, log_dir, device=args.rl_device)
```

并提供 `learn(num_learning_iterations=..., init_at_random_ep_len=...)`；若继续使用现有 `play.py`，还需提供 `load()`、`get_inference_policy()` 及兼容的策略导出方式。配置中的 `runner_class_name` 改为 `"OffPolicyRunner"`，并在 `humanoid/utils/task_registry.py` 的模块作用域导入该类，否则其 `eval()` 同样无法解析名字。请给 off-policy 算法注册独立的任务和实验目录。

## 6. 接入检查清单

- 原来的 `pai_ppo` 未被覆盖，新任务名能被 `--task` 选中。
- 新算法类在使用 `eval()` 的 Runner 文件中已导入；新 Runner 类在 `task_registry.py` 中已导入。
- 配置字段与算法构造参数匹配；Actor、Critic、动作维度与环境匹配。
- `update()` 的返回值、checkpoint 保存和 `play.py` 的加载/导出接口匹配。
- 小规模训练能完成、loss 有限、checkpoint 可加载。
- 导出的策略在 Isaac Gym `play.py` 和 MuJoCo `sim2sim.py` 中使用相同的观测归一化、历史帧顺序和动作/关节顺序。
